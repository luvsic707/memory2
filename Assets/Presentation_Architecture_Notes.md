# 项目架构与技术总结 (Technical Architecture)

## 1. 结构化与抽象 (Structured Data & Abstraction)
**【核心结论】**
* 抛弃零散变量，全面采用 Unity `ScriptableObject` 进行数据结构化设计（Data-Driven Design）。
* 封装通用接口，底层逻辑与表现层解耦，实现高度的代码复用与抽象。

**【🎤 演讲说辞】**
“在我们的架构中，为了避免混乱的数据管理，我们做了深度的**结构化与抽象**。例如，游戏中的旁白内容、音频引用、以及数值配置，我们没有写碎在各个脚本里，而是彻底抽象出了 `NarrationDatabase` 这样的 `ScriptableObject` 数据结构。
这意味着我们的数据脱离了具体的场景，变成了可以在内存中任意流转和强类型的‘资产（Asset）’。同时，我们对功能进行了高度抽象，比如门的显隐、物体的溶解效果（MeltController），全都封装成了具备 `Show()`、`StartMeltNow()` 等方法的独立黑盒模块。调用方完全不需要知道它底层是修改 Mesh 还是操作 Shader_GlobalFloat，实现了完美的抽象封装。”

---

## 2. 解耦设计 (Decoupled Design)
**【核心结论】**
* 摒弃传统的“组件强引用（Hard References）”，构建了**纯事件驱动架构（Event-Driven Architecture）**。
* 遵循 MVC / 关注点分离原则，控制流（Sequence Manager）与表现层（Audio/Shader）完全剥离。

**【🎤 演讲说辞】**
“在解耦设计上，我们引以为傲的是这套**事件驱动架构**。在早期的原型里，我们的‘节点控制器’需要直接拿到‘特效控制器’的组件句柄才能让它执行，这造成了极高的耦合度。
所以我们专门引入了 `NarrationAnnouncer` 这样的**全局事件总线（Event Bus）**。剧本控制脚本（Director）现在只负责掐表计时，时间一到，它只向全系统广播一句毫无情感的 `StartMelt` 或者 `Act_Three` 字符串；而位于听众端的音频播放器和场景响应器独立订阅这些事件并各自干活。**剧本不知道谁在发光，发光的也不知道谁在喊它**，这就是极度优雅的关注点分离与绝对解耦。”

---

## 3. 配置驱动 (Configuration Driven)
**【核心结论】**
* 全面消除代码硬编码（No Hardcoding），将运行逻辑交由外部配置驱动。
* 通过大前端 Inspector 面板暴开配置参数，以及利用配置文件/环境流来管理后端模型/API。

**【🎤 演讲说辞】**
“我们的产品极其强调**配置驱动**理念。大家在以往开发中很容易犯的错就是把‘等待 10 秒’或特定的音频 ID 直接**硬编码（Hardcode）**在 C# 脚本里。而我们彻底重构了这一点，将所有的触发 ID、延迟时间、甚至特定效果的触发时机，全部暴露给了引擎面板（Inspector）配置或外部数据表。
除此之外，在涉及外部 AI 交互和后端扩展的地方，我们也绝不把 API Key 或底层大模型（Model）的名字硬写死在代码里，而是通过读取环境变量（Env）或专门的安全配置文件来管理。这使得我们在不修改代码的情况下，通过纯调参，就能编演出全新的游戏流程或秒切背后的 AI 模型。”

---

## 4. 系统韧性与错误处理 (Resilience & Debugging)
**【核心结论】**
* 构建健壮的防御性编程防线，依靠“惰性初始化（Lazy Initialization）”与异常捕获确保主进程稳定。
* 实装了颗粒度极细的标签化系统日志（Tagged Logging），实现状态机变更的极速追溯。
* 利用协程（Coroutine）分帧算法消除性能毛峰，确立了适应高并发与波动的线上可部署性。

**【🎤 演讲说辞】**
“在产品的韧性与可部署性方面，我们投入了极大的精力以应对真实的外部压力：
首先是**显式错误处理**。代码库全面落实了防御性编程——假如后端 AI 生成由于弱网发生超时，或者运行时前端物体的状态序列发生意外颠倒，我们的脚本统统具备自我急救与容错捕获能力。例如重要组件找不到依赖参数时，系统绝不会抛出致命 Null Reference 而直接闪退，而是走优雅降级的保底流程并输出结构化警告。
其次是**日志系统**。项目里所有的重状态扭转，例如 `[Director]` 控制流推进、`[Narrator]` 语音流状态、以及 `[EventResponder]` 微服务级的广播派发，全部输出携带业务标签的格式化日志。这保证了哪怕在编译打包后的黑盒环境中，也能拥有一条一眼到底的时间追踪轴。
最后，在**部署压力准备**方面，我们深度利用了引擎底层的非阻塞协程机制，彻底避免了由于长连接等待引起的主线程死锁；并且，对于诸如大批量碰撞网格加载这种绝对会造成 CPU 卡顿的操作，我们甚至撰写了‘按帧切分（Slicing per frame）’的高性能均摊统筹算法。不仅跑得通，更抗得了压，产品在性能表现上完全达到了真实世界的上线可部署（Deployment Ready）标准。”
